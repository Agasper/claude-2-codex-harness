# Codex через codexctl

Проектирование, ресёрч и ревью — на мне; написание кода по спеке — на Codex. Запуск Codex идёт **только** через `codexctl`.

## Железное правило: никогда не вызывать `codex` напрямую

У `codex` взаимоисключающие и несогласованные флаги, и каждый самодельный вызов — это лотерея. Реальные грабли, на которых мы уже стояли:

- `--approve-for-me` конфликтует с `-s` и молча роняет запуск;
- у `codex exec resume` **нет** ни `--cd`, ни `-s` — те же флаги, что работают в `codex exec`, там ломают команду;
- забытый `-o` оставляет без финального ответа, забытый `--json` — без лога, по которому можно понять, что происходит.

Всё это зашито внутрь `codexctl` один раз. Снаружи — пять режимов и несколько флагов, перепутать нечего. Если кажется, что нужного режима нет, — это повод дописать `codexctl`, а не собрать вызов `codex` руками.

## Режимы

```
codexctl run     --cwd DIR (--prompt TEXT | --prompt-file F) [--model M]
codexctl review  --cwd DIR [--base REF] [--prompt TEXT] [--model M]
codexctl resume  --id ID (--prompt TEXT | --prompt-file F)
codexctl status  [--id ID]
codexctl result  [--id ID]
codexctl cancel  [--id ID]
codexctl list
```

Если `codexctl` не найден в PATH (не выполнялся `/codex-bridge:setup`), вызывать по полному пути — `"${CLAUDE_PLUGIN_ROOT}/scripts/codexctl.sh"`, а пользователю предложить один раз выполнить `/codex-bridge:setup`.

Без `--id` команды работают с последним прогоном. Песочница, доступ к сети и к `.git`, вырезание переменных Claude Code, метка отката, лог событий — внутри, обсуждать и упоминать это в каждом прогоне не нужно.

## Как запускать

`run`, `review` и `resume` блокируют до конца работы. Запускать их **только** через Bash с `run_in_background: true`.

Почему именно так: фоновая задача Claude Code сама пришлёт уведомление о завершении, и её вывод виден пользователю в интерфейсе. Если вместо этого воспользоваться `nohup`, `&` или `disown`, процесс оторвётся от сессии: уведомления не будет, статус не виден, и мы с пользователем будем ждать давно закончившийся прогон. **Никаких `nohup`, `&`, `disown`, `setsid` — только `run_in_background`.**

Пока прогон идёт, на вопрос «как он там» отвечать через `codexctl status` — он показывает состояние, время последнего события и последние шаги. Не пересказывать своими словами, не гадать.

## Состояния и что с ними делать

| Состояние | Что значит | Что делать |
|---|---|---|
| РАБОТАЕТ | события идут | ничего, доложить последний шаг |
| МОЛЧИТ | нет событий дольше 3 минут | сказать пользователю прямо, показать последний шаг, предложить `codexctl cancel` |
| ГОТОВ | завершился штатно | приёмка |
| УПАЛ | ненулевой код возврата | показать хвост `err.log`, разобрать причину |
| ОБОРВАЛСЯ | нет `turn.completed` | Codex умер на середине; приёмка того, что успел, затем `codexctl resume` |

Отдельно: «ГОТОВ» не значит «сделал». Codex может штатно завершиться, доложив, что не смог. Всегда сверять его слова с фактическими изменениями.

## Дисциплина вокруг прогона

1. **Спека.** Если пользователь дал документ — передаём `--prompt-file` с путём к нему, содержимое не пересказываем. Если спека родилась в диалоге — пишу её сам, **показываю пользователю и жду подтверждения**, потом запускаю. Это единственная точка, где ошибку понимания ещё можно поймать бесплатно.
2. **Чистое дерево.** Если в проекте есть незакоммиченные изменения, сказать об этом до запуска: иначе при приёмке не отличить работу Codex от того, что лежало раньше. Метку отката `codexctl` ставит сам.
3. **Приёмка.** `codexctl result`, затем `git diff` от метки. Если Codex пишет «тесты проходят» — найти в логе прогона соответствующую команду и её вывод. Верить словам без сверки нельзя.
4. **Ревью — никогда автоматически.** После приёмки доложить результат и напомнить про ревью, спросив, кем: мной или `codexctl review`. Ответ «не надо» закрывает тему сразу.

## Чего не делать

- Не вызывать `codex` напрямую и не изобретать флаги.
- Не запускать через `nohup`/`&`/`disown`.
- Не коммитить и не пушить результат Codex без явной просьбы.
- Не запускать Codex на задаче, объяснённой словами в чате, — это моя работа.
- Не докладывать «готово», не посмотрев изменения.
- Не пересказывать пользователю встроенные меры (песочница, фильтрация окружения, метки) — они работают сами.
